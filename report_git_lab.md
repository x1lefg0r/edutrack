## 1. Устройство рабочего каталога, индекса, репозитория, роль HEAD и веток

**Что это:**  
Git работает с тремя «зонами»:

- **Working directory** — файлы, которые ты видишь и редактируешь на диске.
- **Index (staging area)** — промежуточная зона. `git add` перемещает изменения сюда перед коммитом.
- **Repository (.git/)** — база данных всех коммитов и объектов.
- **HEAD** — указатель на текущий коммит (обычно на последний коммит активной ветки).
- **Ветки** — именованные указатели на конкретные коммиты.

**Как проверить:**

```bash
git status           # показывает состояние рабочего каталога и индекса
ls .git/             # содержимое репозитория
cat .git/HEAD        # смотрим на что указывает HEAD
```

> 📸 **[СКРИНШОТ 1]** — вывод `git status` и `ls .git/`

## 2. Файл .gitignore

**Что это:**  
Файл `.gitignore` содержит список файлов и папок, которые Git **не должен отслеживать**. Полезно для `node_modules`, `.env`, файлов сборки и т.д. Поддерживает glob-паттерны: `*.log`, `dist/`, `**/*.tmp`.

**Как проверить:**

```bash
cat .gitignore       # посмотреть текущий .gitignore проекта
git status           # убедиться, что node_modules и прочее не отслеживается
```

> 📸 **[СКРИНШОТ 2]** — содержимое `.gitignore` + `git status` без лишних файлов

## 3. Переход к конкретному коммиту — `git checkout <hash>`

**Что это:**  
Позволяет «переместиться во времени» к любому коммиту в истории. HEAD при этом переходит в состояние **detached HEAD** — не указывает ни на одну ветку. Изменения не теряются, это просто просмотр.

**Как проверить:**

```bash
git log --oneline                    # смотрим историю и выбираем хэш
git checkout af7f0fa                 # переходим к коммиту "refactor: added some a11y"
cat .git/HEAD                        # HEAD теперь содержит хэш, не ветку
git checkout master                  # возвращаемся обратно
```

> 📸 **[СКРИНШОТ 3]** — вывод `git checkout af7f0fa` с предупреждением о detached HEAD

## 4. Переход на другую ветку — `git checkout <branch>`, `git switch <branch>`

**Что это:**  
Переключает активную ветку. `git switch` — более современная и безопасная альтернатива `git checkout` именно для веток. Новую ветку можно создать флагами `-b` / `-c`.

**Как проверить:**

```bash
git branch                           # список веток
git checkout -b lab-git-demo         # создаём и переходим в новую ветку (старый способ)
git switch master                    # возвращаемся на master (новый способ)
git switch -c lab-demo-2             # создаём и переходим (новый способ)
git switch master                    # возвращаемся
git branch -d lab-git-demo lab-demo-2  # удаляем тестовые ветки
```

> 📸 **[СКРИНШОТ 4]** — создание ветки и переключение между ними

## 5. Отмена изменений через новый коммит — `git revert <hash>`

**Что это:**  
`git revert` создаёт **новый коммит**, который отменяет изменения указанного коммита. В отличие от `reset`, история не переписывается — это безопасный способ отмены, особенно для уже запушенных коммитов.

**Как проверить:**

```bash
git log --oneline                    # выбираем коммит для отмены
git revert 2d9b048 --no-edit        # отменяем "fix: fixed pagination page"
git log --oneline                    # видим новый revert-коммит в истории
git revert HEAD --no-edit           # отменяем только что созданный revert (возвращаем всё как было)
```

> 📸 **[СКРИНШОТ 5]** — `git log --oneline` с появившимся revert-коммитом

## 6. Режим `--soft` и `--hard` для `git reset`

**Что это:**  
`git reset` перемещает HEAD (и ветку) назад по истории.

- `--soft` — коммит отменяется, но изменения **остаются в индексе** (готовы к повторному коммиту).
- `--hard` — коммит отменяется и изменения **полностью удаляются** из рабочего каталога. Опасная операция!

**Как проверить:**

```bash
# Тест --soft
git log --oneline
git reset --soft HEAD~1              # отменяем последний коммит, файлы остаются в staging
git status                           # видим файлы в staged
git commit -m "chore: added readme"  # возвращаем коммит обратно

# Тест --hard (осторожно!)
git reset --hard HEAD~1              # полностью удаляем последний коммит
git log --oneline                    # коммита больше нет
git reset --hard c058d5c             # восстанавливаем по хэшу (из reflog)
```

> 📸 **[СКРИНШОТ 6]** — разница в `git status` после `--soft` и после `--hard`

## 7. Изменить сообщение последнего коммита — `git commit --amend`

**Что это:**  
`--amend` позволяет изменить последний коммит: его сообщение и/или содержимое. Важно: **не использовать для уже запушенных коммитов** — это перезаписывает историю.

**Как проверить:**

```bash
git log --oneline                            # смотрим последний коммит
git commit --amend -m "chore: added readme"  # исправляем сообщение
git log --oneline                            # видим обновлённое сообщение
```

Или интерактивно (откроется редактор):

```bash
git commit --amend                           # редактор для изменения сообщения
```

> 📸 **[СКРИНШОТ 7]** — `git log --oneline` до и после `--amend`

## 8. Содержимое HEAD — `cat .git/HEAD`

**Что это:**  
Файл `.git/HEAD` — это текстовый файл с одной строкой. Обычно содержит ссылку на ветку (`ref: refs/heads/master`). В состоянии detached HEAD содержит хэш коммита напрямую.

**Как проверить:**

```bash
cat .git/HEAD                        # покажет: ref: refs/heads/master
git checkout af7f0fa                 # переходим к конкретному коммиту
cat .git/HEAD                        # покажет хэш коммита (detached HEAD)
git switch master                    # возвращаемся
cat .git/HEAD                        # снова: ref: refs/heads/master
```

> 📸 **[СКРИНШОТ 8]** — вывод `cat .git/HEAD` в обычном режиме и в detached HEAD

## 9. Куда указывает ветка — `cat .git/refs/heads/master`

**Что это:**  
Каждая ветка — это просто файл в `.git/refs/heads/`, содержащий SHA-1 хэш коммита, на который она указывает. Когда делается новый коммит, этот файл обновляется автоматически.

**Как проверить:**

```bash
cat .git/refs/heads/master           # выведет хэш последнего коммита ветки
git log --oneline -1                 # должен совпадать с хэшем выше
```

> 📸 **[СКРИНШОТ 9]** — совпадение хэша из файла и из `git log`

## 10. Команда `git log --oneline`

**Что это:**  
Компактный просмотр истории коммитов — каждый коммит в одну строку: короткий хэш + сообщение. Удобно для быстрой навигации. Можно комбинировать с `--graph`, `--all`, `-N` (количество коммитов).

**Как проверить:**

```bash
git log --oneline                    # вся история компактно
git log --oneline -5                 # последние 5 коммитов
git log --oneline --graph --all      # граф веток
```

> 📸 **[СКРИНШОТ 10]** — вывод `git log --oneline --graph --all`

## 11. Команды `git diff` и `git diff <hash>`

**Что это:**  
`git diff` показывает **что именно изменилось** в файлах.

- `git diff` — изменения в рабочем каталоге (не добавленные в индекс).
- `git diff --staged` — изменения в индексе (то, что пойдёт в коммит).
- `git diff <hash>` — разница между текущим состоянием и указанным коммитом.
- `git diff <hash1> <hash2>` — разница между двумя коммитами.

**Как проверить:**

```bash
git diff                             # нет изменений (чистый репозиторий)
git diff 2d9b048                     # разница с коммитом "fix: fixed pagination page"
git diff 1ea8432 c058d5c             # разница между двумя коммитами
git diff HEAD~1 HEAD                 # разница последних двух коммитов
```

> 📸 **[СКРИНШОТ 11]** — вывод `git diff HEAD~1 HEAD`

## 12. Команда `git rm --cached <файл>`

**Что это:**  
Удаляет файл из **индекса** (перестаёт отслеживаться Git), но оставляет его на диске. Используется, когда нужно добавить файл в `.gitignore` уже после того, как он был закоммичен.

**Как проверить:**

```bash
touch test_temp.txt                  # создаём тестовый файл
git add test_temp.txt                # добавляем в индекс
git status                           # файл в staged
git rm --cached test_temp.txt        # убираем из индекса
git status                           # файл теперь untracked
rm test_temp.txt                     # убираем с диска
```

> 📸 **[СКРИНШОТ 12]** — `git status` до и после `git rm --cached`

## 13. Команда `git stash`

**Что это:**  
Позволяет временно «спрятать» незакоммиченные изменения, чтобы переключиться на другую ветку или задачу. Изменения кладутся в стек и могут быть восстановлены позже.

**Как проверить:**

```bash
echo "temp change" >> README.md      # вносим изменение
git status                           # видим изменённый файл
git stash push -m "temp readme edit" # прячем изменения
git status                           # рабочий каталог чист
git stash list                       # список спрятанных изменений
git stash pop                        # достаём последнее спрятанное
git status                           # изменения вернулись
git checkout -- README.md            # откатываем тестовое изменение
```

Дополнительно:

```bash
git stash apply stash@{0}            # применить без удаления из стека
git stash branch new-feature-branch  # создать ветку из stash
```

> 📸 **[СКРИНШОТ 13]** — `git stash list` и `git stash pop`

## 14. Восстановление удалённого через `reset --hard` коммита

**Что это:**  
`git reflog` хранит лог **всех перемещений HEAD**, даже тех коммитов, которые «потеряны» после `reset --hard`. Это «страховая сетка» — с помощью рефлога можно восстановить почти что угодно в течение 90 дней.

**Как проверить:**

```bash
git log --oneline                         # запоминаем текущий хэш
git reset --hard HEAD~1                   # "удаляем" последний коммит
git log --oneline                         # коммита нет
git reflog                                # видим потерянный коммит в reflog
git reset --hard c058d5c                  # восстанавливаем по хэшу
git log --oneline                         # коммит вернулся

# Альтернатива — восстановить в новую ветку:
# git switch -c recovered c058d5c
```

> 📸 **[СКРИНШОТ 14]** — `git reflog` с видимым "потерянным" коммитом

## 15. Команда `git cherry-pick`

**Что это:**  
Применяет изменения из **конкретного коммита** другой ветки в текущую. В отличие от merge/rebase, берётся ровно один (или несколько) выбранных коммитов.

**Как проверить:**

```bash
git checkout -b cherry-demo          # создаём тестовую ветку
git switch master                    # возвращаемся на master
git cherry-pick af7f0fa              # берём коммит "refactor: added some a11y" в master
git log --oneline                    # видим перенесённый коммит
git revert HEAD --no-edit            # отменяем cherry-pick
git branch -d cherry-demo            # удаляем ветку
```

> 📸 **[СКРИНШОТ 15]** — `git log --oneline` с перенесённым коммитом

---

## 16. Объединение нескольких коммитов в один (squash)

**Что это:**  
Позволяет «склеить» несколько коммитов в один. Полезно для чистоты истории перед merge в main.

- `git rebase -i HEAD~N` — интерактивный rebase: `squash` оставляет изменения + объединяет сообщения, `fixup` оставляет только сообщение первого.
- `git reset --soft HEAD~N` + новый коммит — более простой способ без интерактивного режима.

**Как проверить (через reset --soft):**

```bash
git log --oneline                    # смотрим последние коммиты
git reset --soft HEAD~2              # "разворачиваем" 2 коммита в staged
git status                           # все изменения в индексе
git commit -m "chore: squashed last 2 commits"  # один новый коммит
git log --oneline                    # вместо 2 — один коммит
git reset --soft HEAD~1              # возвращаем как было
git commit -m "chore: added readme"  # восстанавливаем исходный коммит
```

**Через rebase -i (интерактивно):**

```bash
git rebase -i HEAD~3                 # откроется редактор с последними 3 коммитами
# Меняем pick → squash у нужных строк, сохраняем
```

> 📸 **[СКРИНШОТ 16]** — `git log --oneline` до и после squash

## 17. Перенос коммитов в новую ветку — `git rebase --onto`

**Что это:**  
`git rebase --onto <newbase> <upstream> <branch>` переносит серию коммитов из одной ветки в другую. Полезно, если ветка была создана не от того места, или нужно перенести часть коммитов.

**Как проверить:**

```bash
git checkout -b feature-a 1ea8432   # создаём ветку от старого коммита
git switch master
git checkout -b feature-b            # создаём ветку от master
# rebase переносит коммиты feature-a на master, начиная от 1ea8432
git rebase --onto master 1ea8432 feature-a
git log --oneline feature-a          # коммиты теперь на master
git branch -d feature-a feature-b    # чистим тестовые ветки
```

> 📸 **[СКРИНШОТ 17]** — `git log --oneline` ветки до и после `rebase --onto`

## 18. Команда `git blame`

**Что это:**  
Показывает для каждой строки файла: **кто**, **когда** и в **каком коммите** её написал. Незаменимо для поиска причин появления конкретной строки кода.

**Как проверить:**

```bash
git blame README.md                  # кто написал каждую строку README
git blame -L 1,10 README.md          # только строки 1-10
git blame --date=short README.md     # с короткой датой
```

> 📸 **[СКРИНШОТ 18]** — вывод `git blame README.md`

## 19. Команда `git bisect`

**Что это:**  
Помогает найти коммит, который **сломал** что-то, методом **бинарного поиска**. Ты указываешь «плохой» (с багом) и «хороший» (без бага) коммиты, а Git поочерёдно предлагает коммиты для проверки, сужая диапазон вдвое каждый раз.

**Как проверить:**

```bash
git bisect start                     # начинаем поиск
git bisect bad                       # текущий коммит — плохой
git bisect good 540d787              # этот коммит — хороший (начало репозитория)
# Git переключит HEAD на серединный коммит — проверяем и говорим good/bad
git bisect good                      # или: git bisect bad
# Повторяем, пока Git не найдёт первый плохой коммит
git bisect reset                     # выходим из режима bisect
```

Для автоматизации:

```bash
git bisect start HEAD 540d787        # bad=HEAD, good=540d787
git bisect run npm test              # автоматически запускает тесты на каждом шаге
git bisect reset
```

> 📸 **[СКРИНШОТ 19]** — вывод `git bisect` с найденным коммитом
